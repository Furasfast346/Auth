# Auth System — система аутентификации и авторизации

Бэкенд на **FastAPI** с JWT-аутентификацией, ролевой моделью доступа (RBAC), админ-панелью и полным CRUD для пользователей, товаров и ролей.

## Стек технологий

- **FastAPI** — веб-фреймворк
- **SQLAlchemy 2.0** — асинхронная ORM
- **SQLite** — база данных
- **JWT (PyJWT)** — токены доступа
- **bcrypt** — хэширование паролей
- **Pytest** — тестирование
- **Docker** — контейнеризация
- **HTML/CSS/JS** — фронтенд (демонстрация)

## Установка и запуск

### Локальный запуск

```bash
# Клонировать репозиторий
git clone https://github.com/Furasfast346/Auth.git
cd Auth

# Создать виртуальное окружение
python -m venv venv
source venv/bin/activate  # или venv\Scripts\activate на Windows

# Установить зависимости
pip install -r requirements.txt

# Запустить сервер
python -m app.main
```

### Запуск через Докер
```
docker build -t auth-system .
docker run -p 8000:8000 auth-system
```

## Основные возможности
- Регистрация и логин с выдачей JWT-токена
- Мягкое удаление аккаунта (is_active = False)
- Ролевая модель доступа (RBAC)
- Административная панель:
- Управление пользователями (активация, блокировка, назначение ролей)
- Управление ролями (создание, редактирование, удаление)
- Управление разрешениями (создание, удаление)
- Назначение разрешений ролям
- CRUD для товаров с проверкой прав
- Автоматическая документация Swagger

## Система разграничения прав доступа (RBAC)

###  Схема структуры управления доступом

В системе реализована **ролевая модель доступа (RBAC)**. Права доступа назначаются не напрямую пользователям, а через роли. Это позволяет гибко управлять правами групп пользователей.

###  Таблицы в базе данных

| Таблица | Описание |
|---------|----------|
| `users` | Пользователи системы (email, пароль, ФИО, активен/заблокирован) |
| `roles` | Роли (`admin`, `manager`, `user`) |
| `permissions` | Разрешения (`users:read`, `products:write`, и т.д.) |
| `user_roles` | Связь пользователей и ролей (многие ко многим) |
| `role_permissions` | Связь ролей и разрешений (многие ко многим) |

###  Тестовые данные

При первом запуске база данных автоматически заполняется тестовыми данными:

**Роли:**
| id | name |
|----|------|
| 1 | admin |
| 2 | manager |
| 3 | user |

**Разрешения:**
| id | name |
|----|------|
| 1 | users:read |
| 2 | users:write |
| 3 | products:read |
| 4 | products:write |
| 5 | products:delete |

**Связи ролей и разрешений:**

| Роль | Разрешения |
|------|------------|
| **admin** | все разрешения (`users:read`, `users:write`, `products:read`, `products:write`, `products:delete`) |
| **manager** | `products:read`, `products:write`, `products:delete` |
| **user** | `products:read` |

**Тестовый пользователь:**
| Email | Пароль | Роль |
|-------|--------|------|
| admin@example.com | admin123 | admin |

###  Как работает проверка доступа

1. **Пользователь не авторизован** (нет JWT-токена или токен невалиден):
   - Любой запрос к защищённому эндпоинту → **ошибка 401 Unauthorized**

2. **Пользователь авторизован, но не имеет нужного разрешения:**
   - Например, пользователь с ролью `user` пытается создать товар (`products:write`) → **ошибка 403 Forbidden**

3. **Пользователь авторизован и имеет нужное разрешение:**
   - Запрос обрабатывается, возвращается запрашиваемый ресурс

### 💻 Реализация в коде

Проверка прав выполняется через кастомную зависимость `require_permission`:

```python
@router.get("/products/")
async def get_products(
    session: SessionDep,
    current_user: User = Depends(require_permission("products:read"))
):
    return await session.execute(select(Product)).scalars().all()
```
